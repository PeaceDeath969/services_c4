

# Marketplace Architecture (C4 + Docker)

## Описание

Здесь описана архитектура маркетплейса, где:

- продавцы публикуют товары  
- пользователи смотрят ленту  
- оформляют заказы  
- оплачивают  
- получают уведомления  

Также поднят один сервис на FastAPI с endpoint `/health`.

---

# Архитектура

Диаграмма: `workspace.likec4`  
Формат: C4 Container  

Архитектура построена с разделением доменов на отдельные сервисы и использованием брокера событий для асинхронного взаимодействия.

---

# Домены

1. Users — пользователи и роли  
2. Catalog — товары  
3. Feed — лента и персонализация  
4. Orders — заказы и статусы  
5. Payments — обработка оплаты  
6. Notifications — уведомления  

---

# Сервисы

Каждый домен выделен в отдельный сервис:

- API Gateway (единая точка входа)
- User Service
- Catalog Service
- Feed Service
- Order Service
- Payment Service
- Notification Service
- Message Broker (для событий)

Почему так:
- понятное разделение ответственности  
- можно масштабировать сервисы независимо  
- нет общей базы данных между сервисами  

---

# Владение данными

У каждого сервиса своя база данных:

- User Service → Users DB  
- Catalog Service → Catalog DB  
- Feed Service → Feed DB  
- Order Service → Orders DB  
- Payment Service → Payments DB  
- Notification Service → Notify DB  

Общая база данных не используется.

---

# Взаимодействие

Синхронно (HTTP):

- UI → API  
- API → сервисы  
- Payment → внешний платёжный провайдер  
- Notification → внешний сервис отправки сообщений  

Асинхронно (через брокер):

- Order Service публикует события создания и изменения заказа  
- Payment Service публикует события результата оплаты  
- Catalog Service публикует события обновления товаров  
- Notification и Feed подписываются на события  

---

# Альтернативы

## 1. Микросервисы (выбранный вариант)

Плюсы:
- гибко развивать домены  
- проще масштабировать по частям  
- изоляция ответственности  

Минусы:
- инфраструктура и поддержка сложнее  

## 2. Модульный монолит

Плюсы:
- проще разработка  
- проще деплой  

Минусы:
- сложнее масштабировать  
- сильная связанность модулей и общей базы  

---

# Почему выбран микросервисный вариант

Маркетплейс обычно растёт по нагрузке и функционалу, и удобно, когда домены можно развивать и масштабировать отдельно. Поэтому микросервисная архитектура здесь выглядит логичнее.
